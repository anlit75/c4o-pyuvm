# Guide

*[繁體中文](guide.zh-TW.md)*

How the verification in this repository works, and what went wrong on the way to
it. The [README](../README.md) is what it is and how to run it; this is why it
looks the way it does.

## The environment

Four hand-written files, 623 lines, and one idea: drive the DUT through its pins
and nothing else.

```
test/apb_agent.py   143  ApbTxn, driver, monitor, agent, and the register adapter
test/uart_env.py    197  the environment, the scoreboard, and the test base class
test/test_uart.py   137  the data-path tests
test/test_ral.py    146  the register tests
test/uart_ral.py    150  GENERATED by make ral
```

**The driver is not a state machine.** APB3 is two phases, and this DUT ties
`PREADY` high unconditionally (`assign PREADY = 1'b1`), so there is no
backpressure to model: setup, access, read `PRDATA` at the edge that ends the
access phase, drop `PSEL`. Three cycles, every time. The monitor is the same
observation from the other side — it watches for the cycle where `PSEL`, `PENABLE`
and `PREADY` are all set, and broadcasts what it saw.

**The scoreboard never looks at the serial line.** `tx_o` is tied back to `rx_i`,
so every byte written to THR has to reappear, in order, from RBR. That single
relation covers the APB decode, the TX FIFO, the serialiser, the deserialiser and
the RX FIFO. Modelling the bit timing instead would mean asserting the DUT's
divisor arithmetic against a second copy of the same arithmetic — which proves
nothing, and breaks every time the divisor changes.

It does have to follow the register writes. At offset `0x0` a write is THR and a
read is RBR, but **only while `LCR[7]` is clear**: with DLAB set the same address
is the divisor latch and has nothing to do with the FIFOs. The scoreboard tracks
that bit so it knows which reads are data.

**The loopback is a coroutine, not a wire.**

```python
async def tie_tx_to_rx():
    dut.rx_i.value = dut.tx_o.value
    while True:
        await Edge(dut.tx_o)
        dut.rx_i.value = dut.tx_o.value
```

cocotb elaborates the DUT as the root — there is no testbench module to do the tie
in — so Python does it. That turns out to be the better answer anyway: it works
identically on the netlist, where a Verilog wrapper would not exist.

It is driven off `tx_o` changing rather than off the clock, and that was a fix
rather than a first draft. A clocked mirror reads `tx_o`'s pre-edge value and so
adds a cycle of latency to the serial line. The RTL tolerates it; the netlist,
compiled with `-DUNIT_DELAY` where every cell costs a step, has less room — a bit
is only `DIVISOR + 1` = 5 cycles wide.

## Proving a test can fail

A test that has never failed is a test nobody has checked. Every test here was
run against a deliberately broken design, and the point is not that they all went
red — it is **which** ones did.

Six mutations of the DUT, each applied, run under `RANDOM_SEED=4242`, reverted:

| mutation | `reset_values` | `register_readback` | `idle_status` | `loopback` | `random_bytes` | `burst` |
|---|---|---|---|---|---|---|
| IIR resets to `0b0000` | **FAIL** | PASS | PASS | PASS | PASS | PASS |
| LSR resets to `0x00` | PASS | PASS | PASS | PASS | PASS | PASS |
| an LCR write drops bit 0 | PASS | **FAIL** | PASS | FAIL | FAIL | FAIL |
| an IER write lands in MCR | PASS | **FAIL** | PASS | PASS | PASS | PASS |
| `LSR.THRE` never asserts | FAIL | PASS | **FAIL** | PASS | PASS | PASS |
| `LSR.TEMT` never asserts | FAIL | PASS | **FAIL** | PASS | PASS | PASS |

and five more aimed at the data path:

| mutation | `loopback` | `random_bytes` | `burst` |
|---|---|---|---|
| THR write drops its low bit | FAIL | FAIL | FAIL |
| `LSR[0]` (data ready) tied low | FAIL | FAIL | FAIL |
| an RBR read never pops the RX FIFO | **PASS** | FAIL | FAIL |
| the TX FIFO holds one byte, not sixteen | **PASS** | **PASS** | FAIL |
| the monitor never reports a transfer | FAIL | FAIL | FAIL |

Read the columns, not the rows. Each **PASS** in bold is a test that could not see
the bug, and therefore the reason the next test exists:

*   **One byte cannot tell a queue from a register.** `loopback` sends `0xA5` and
    reads it back; with the RX FIFO never popping, it reads the same correct byte.
    `random_bytes` sends twenty and fails on the second.
*   **Sending bytes one at a time never puts two in the FIFO at once.** Only
    `burst`, which writes all sixteen before reading any, can see a depth of one.
*   **The right value at the wrong address is invisible to the data path.** An IER
    write redirected to MCR changes nothing the UART transmits. The mirror catches
    it: `Register 'regs.IER' value read from DUT (0x0) does not match mirrored
    value (0x5)`. That row is the argument for having a register model at all.
*   **One mutation is aimed at the testbench, not the DUT.** With the monitor
    silenced, every scoreboard check would pass on an empty queue — so the test
    base class asserts the count instead: `the scoreboard matched 0 bytes through
    the loopback, not 1`.

**And one mutation survives.** Changing LSR's reset from `0x60` to `0x00` breaks
nothing, because that reset value is not observable from the bus: `THRE` and
`TEMT` are driven combinationally from `tx_elements` and `tx_ready`, so `regs_n`
overwrites both on the first clock edge after reset. `ResetValuesTest`'s docstring
says so rather than claiming otherwise, and `IdleStatusTest` pins the same two
bits field by field instead — which is why the last two rows of the first table
have a column that fails.

## The register model

`regs/apb_uart.rdl` is the register map in SystemRDL. `make ral` runs
`peakrdl pyuvm` over it, and CI regenerates and diffs the result, so the model the
tests drive and the description of the map cannot drift.

The `.rdl` describes IER, IIR, LCR and LSR. Its header is mostly about what it
**cannot** describe, and that is the interesting part of putting a register
description language against a 1980s peripheral:

1.  **THR/RBR at `0x0` is not a register.** A write pushes into the TX FIFO and a
    read pops the RX FIFO. There is no storage to mirror — write `0xA5` and the
    next read returns whatever the serial line delivered. UVM has `uvm_reg_fifo`
    for this; PeakRDL does not generate it.
2.  **FCR at `0x2` is write-only and shares its address with the read-only IIR.**
    SystemRDL's `alias` is the mechanism for two views of one address — but it is
    a view of *the same storage*, and these are unrelated hardware:

    ```
    error: Alias register 'FCR' contains field 'TX_CLR' that does not exist in
    the primary register.
    ```
3.  **DLL and DLM replace THR and IER while `LCR[7]` is set.** A register's
    address cannot depend on another register's contents.
4.  **MCR, MSR and SCR are absent on purpose.** The RTL resets storage for them
    and then never decodes a read or a write, so they read back as 0 from the
    default branch. Describing them would make the model predict values the design
    cannot return.

`test_uart.py` drives those four through the agent directly, and says so.

### Four things pyuvm needed that PeakRDL does not provide

Each of these was found by a failure, and each is written next to the line that
fixes it:

| | what happens without it |
|---|---|
| the map reconfigured little-endian | PeakRDL creates it with `UVM_NO_ENDIAN`; pyuvm reads that as *no endianness specified*, takes the error branch in `_get_physical_addresses_to_map`, and every access dies on `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'` |
| `lock_model()` | the same failure, after `Map 'regs.reg_map' does not seem to initialized correctly` |
| `set_auto_predict(True)` | the mirror never leaves its reset value: `Register 'regs.LCR' value read from DUT (0x5F) does not match mirrored value (0x0)` |
| `set_sv_uvm_style_reporting_enabled(True)` | the register layer's errors go to a plain `logging` logger named `RegModel` that the report server never counts, so `mirror(UVM_CHECK)` logs a mismatch and **the test passes anyway** |

On the third: a `uvm_reg_predictor` on the monitor is the better setup in general —
it catches writes the register layer did not initiate — and it is the wrong one
*here*. The monitor also sees the FCR traffic the map deliberately does not
describe, and a predictor would feed an FCR write at `0x2` into IIR's mirror,
because IIR is the register the map has at that address.

The reset values the model checks are not ones anybody would guess, and they come
from different mechanisms:

```
IER reads 0x00, .rdl says 0x00
IIR reads 0xc1, .rdl says 0xc1     <- hardwired 0b1100 over iir_q, which resets to 0b0001
LCR reads 0x00, .rdl says 0x00
LSR reads 0x60, .rdl says 0x60
```

The expected value comes from `reg.get_reset()`, not from a number in the test, so
the `.rdl` stays the only place the map is written down.

## Running on the gates

```bash
make gds          # produces runs/<tag>/final/nl/apb_uart_sv.nl.v
make cocotb-gl    # drives it with the same six tests
```

Not a second testbench. The same Python, the same scoreboard, the same register
model, against the netlist and the PDK's own cell models. The usual approach is a
separate gate-level testbench — which is what `make gatesim` wants, and why
`//GATE_TESTS` is absent from `config.yaml`: a second testbench is a second
scoreboard to keep in step with the first, and the moment they drift the
gate-level one stops meaning anything.

It works only because nothing in `test/` touches anything but the top-level ports.
Reach inside the design and this is where you find out, with an `AttributeError`
naming the net synthesis removed. CI runs it on every pull request for that
reason, and it costs three seconds.

**The first thing it caught was a bug in the testbench, not the design.** The
first gate-level run failed in 0.06 ns of simulated time, three tests out of three --
the register tests came later:

```
txn.rdata = int(self.dut.PRDATA.value)
ValueError: Unresolvable bit in binary string: 'x'. Set the COCOTB_RESOLVE_X
environment variable to configure how special values are resolved.
```

A gate-level run compiles the PDK cell models alongside the netlist, and
`sky130_fd_sc_hd.v` carries `` `timescale 1ns/1ps ``. The generated RTL carried no
timescale at all, so Icarus ran it at a precision of one second — and cocotb's
`step` unit *is* that precision. The two-step clock the tests asked for was **2 ps
against the gates and 2 s against the RTL**. At 2 ps with 1 ns of delay per cell
the design never leaves reset, and everything it drives is X.

`make rtl` now writes `` `timescale 1ns / 1ps `` into the generated Verilog and the
tests ask for 10 ns.

**The tempting wrong fix was right there in the error message.**
`COCOTB_RESOLVE_X` would have turned the X into a zero and let every test pass on
a design that was not running. The reads here are of registers the test either
wrote or reset defines, so an X in `PRDATA` is a bug and `int()` raising on it is
the behaviour to keep.

A separate gate-level testbench would have had its own `` `timescale `` and never
compared, so nothing would ever have pointed at the mismatch. That is the case for
one testbench rather than two, and it is not the argument anybody makes for it in
advance.

**What the step asserts** is that the two runs agree:

```
RTL:   TESTS=6 PASS=6 FAIL=0 SKIP=0
gates: TESTS=6 PASS=6 FAIL=0 SKIP=0
```

Identical lines, not a hardcoded count — the count was hardcoded once, at three,
and it went red on three new tests that all passed.

## Closing timing took three wrong answers

The flow reports setup violations as a **warning**, so this repository went green
twice on a design that missed its own clock:

```
setup slack      -0.75 ns  (24 violations)
hold slack       +0.11 ns  (0 violations)
signoff          clean  (Magic DRC, KLayout DRC, LVS, antenna, XOR)
```

Every one of the 24 violations ended at a **port**:

```
Startpoint: uart_rx_fifo_i.pointer_out[1] (rising edge-triggered flip-flop)
Endpoint: PRDATA[4] (out)
                             8.502929   data arrival time
               10.000000    10.000000   clock CLK (rise edge)
               -0.250000     9.750000   clock uncertainty
               -2.000000     7.750000   output external delay
                             7.750000   data required time
                            -0.752928   slack (VIOLATED)
```

`IO_DELAY_CONSTRAINT` is 20 in the sky130 defaults — a fifth of every clock period
reserved as external delay on the ports, 2 ns out of 10. That is right for a
design whose pins drive a package and a board. This one is a block: `PRDATA` goes
to an APB master on the same die. It was paying 2 ns for a board that does not
exist.

Five rounds, each a full flow:

| `CLOCK_PERIOD` | `IO_DELAY_CONSTRAINT` | setup slack | violations |
|---|---|---|---|
| 10.0 | 20 | -0.75 ns | 24 |
| **11.0** | 20 | -0.70 ns | 24 |
| 10.0 | **5** | -0.03 ns | 1 |
| 10.0 | 5 | + resizer margin 0.1 — *identical to the row above, to the picosecond* | 1 |
| **11.0** | **5** | **+0.92 ns** | **0** |

**The second row is the trap.** Relaxing the clock period returned only 0.8 ns per
nanosecond, because the I/O budget is a percentage and took a fifth of everything
added. The obvious lever looks broken — and it is the right lever, once the budget
is 5 instead of 20. `required = 0.95 × period − 0.25` rather than
`0.8 × period − 0.25`.

**The fourth row is a coincidence mistaken for a cause.** The remaining slack was
`-0.025290` and `GRT_RESIZER_SETUP_SLACK_MARGIN` defaults to `0.025`, which reads
like the resizer stopping at its margin and detailed routing spending it. Raising
the margin to 0.1 changed arrival, cell count and power *not at all*. The resizer
is not stopping early; it cannot improve that path.

Worth knowing about that path: 2.83 of its 9.28 ns are three `clkdlybuf4s25` cells
the flow inserted to fix **hold**. Almost a third of the setup-critical path is
padding added to solve the opposite problem, and hold slack is only +0.10 ns, so
there is no room to insert less of it. That is the real headroom in this design,
and it is not a constraint away.

So: 90.9 MHz with an honest 0.55 ns port budget, rather than 100 MHz with a port
budget of zero — which closes on paper by asserting that whatever latches `PRDATA`
needs no setup time of its own. Both numbers, and both wrong turns, are written
into `config.yaml` next to the values they concern, because a config file that
records only the answer invites the same three rounds again.

And CI gates it now. `setup slack` or `hold slack` reporting anything but
`(0 violations)` fails the build, after the step that prints the violating paths —
so a failure arrives with its evidence.

## Iterating without re-running the whole flow

The first `make gds` is about five minutes. Most of what you change after it —
`FP_CORE_UTIL`, `CLOCK_PERIOD`, the floorplan — does not need synthesis redone, so
hand LibreLane the flags that resume the last run:

```bash
make gds LIBRELANE_ARGS="--last-run --from floorplan"
```

That reads the previous run out of `runs/`, which is why `make clean` leaves that
directory alone and `make distclean` is the one that removes it.

## Seeing the circuit

```bash
make schematic
```

Draws `build/schematic.svg` — the design as flops, adders and muxes, carrying the
names the RTL gave them. Open it in the browser, or click it in VS Code; it is an
SVG, so nothing special is needed to read it.

It is not a picture of the netlist. `make synth` runs a full synthesis and leaves
hundreds of technology cells, from which nobody has ever learned anything about
their own design. `make schematic` stops earlier, where the circuit still looks
like the code it came from.

Under a second, so it costs nothing to run after every change — unlike `make gds`.

## Working inside the container

The repo ships a [Dev Container](https://containers.dev/). Open it in GitHub
Codespaces, or in VS Code with *Reopen in Container*, and you get the same image
CI uses, with the Verilog extensions already installed. The `Makefile` notices it
is already inside the container and calls the tools directly instead of nesting
another one.

`make gds` works in here too: the container ships a Docker daemon of its own for
the LibreLane sidecar. If `make gds` says it cannot find one, rebuild the Dev
Container — that is what it is asking for.

Two things to know:

*   **It runs as `root`.** On a Linux host that means files it writes into
    `build/` end up owned by `root`, so `make clean` from your host may need
    `sudo`. Running as a normal user instead breaks Codespaces.
*   **Watch the disk in a Codespace.** The inner daemon has its own image store,
    so the LibreLane image is pulled again rather than shared with the host, and
    the Sky130 PDK is another 3GB on top. On the smallest Codespace machine that
    is most of the disk — pick a larger one, or run `make gds` from your own host.

Prefer to stay in your own editor? `make shell` drops you into the same image from
any terminal.

## Configuration reference

`config.yaml` is a [LibreLane](https://github.com/librelane/librelane)
configuration file. Keys LibreLane does not own carry a `//` prefix, which it
ignores outright — that is what keeps one file valid for both tools.

| Key | What it does |
|---|---|
| `DESIGN_NAME` | The top module's name. Everything else reads it from here. |
| `VERILOG_FILES` | Synthesisable sources — here, the one file `make rtl` generates. LibreLane validates each entry as a literal path and does not expand `**`. |
| `"//TEST_FILES"` | Verilog testbenches for `make sim`. Globs work. |
| `"//COCOTB_TESTS"` | Python testbenches for `make cocotb` and `make cocotb-gl`. Only the files defining `@cocotb.test()` belong here; the rest of `test/` is imported by them. |
| `CLOCK_PORT` / `CLOCK_PERIOD` | The clock to constrain, and its period in ns. |
| `IO_DELAY_CONSTRAINT` | How much of the period is reserved as external delay on the ports, as a percentage. 5 here, against a default of 20 — see above. |
| `LINTER_DISABLE_WARNINGS` | Verilator warnings waived for the design. Two here, each with its reason next to it. |
| `LINTER_DISABLE_WARNINGS_BLACKBOX` | The same for the PDK's blackbox stubs, which carry no timescale of their own. |
| `ERROR_ON_SYNTH_CHECKS` | Off here, for eight dead self-looping bits in the DUT's register file. CI asserts the reports directly instead. |
| `FP_SIZING` / `FP_CORE_UTIL` | How the die is sized — see below. |
| `PDK` / `STD_CELL_LIBRARY` | Sky130 and its standard cells. Leave alone. |

**The die sizes itself.** `FP_SIZING: relative` floorplans from `FP_CORE_UTIL` —
how full the core should be, 40% here, coming out at 54.2% — so a bigger design
gets a bigger die instead of "does not fit". Lower it if routing is tight, raise it
for a smaller chip.

A fixed die is still available: set `FP_SIZING: absolute` and add
`DIE_AREA: [0, 0, w, h]`. Do not leave `DIE_AREA` in the file under relative
sizing — the flow no longer reads it, but the GDS stream-out still draws the chip
boundary from it, and signoff then fails on a boundary nothing else used.

Everything else in the file belongs to LibreLane; see
[its documentation](https://librelane.readthedocs.io/) for the full list, and the
[c4o-core README](https://github.com/anlit75/c4o-core) for what this engine reads.
